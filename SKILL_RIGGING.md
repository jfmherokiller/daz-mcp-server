# Skill: Rigging Specialist
Attaching non-native geometry to a figure (conforming clothing/hair/props) and authoring
joint-triggered corrective morphs (JCMs), scripted via DazScript. Found and verified live during
the `blender_daz_exporter` project (see `E:\modelStuff\AIHelpers\Daz\DUF_EXPORT_NOTES.md` for the
full investigation log this was distilled from).

## Making an attached mesh actually deform with a figure's pose

**Do NOT hand-author a `conform_target`/independent-skeleton-copy DSON structure expecting it to
deform.** It loads and resolves perfectly (`conform_target` reads back correctly,
`getFollowTarget()` reads back correctly, skin weights load) but produces **zero deformation** on
posing — confirmed live, byte-identical bounding box before/after a pose change, across multiple
independent bug-fix rounds. `conform_target` and `setFollowTarget()` establish the *relationship*
real conforming clothing has, but the actual per-vertex weighting is generated by Daz's own
weight-transfer algorithm, not described declaratively in the file.

**What actually works — Daz's own Transfer Utility, driven entirely by script:**

```javascript
// 1. Import/merge the attachment as a plain PROP (no skeleton at all - a DSON node with
//    "type":"node", not "figure"/"bone"). A merged .duf prop loads instantly with no dialog.
//    Do NOT use OBJ import for this (see gotcha below).
var propNode = Scene.findNodeByLabel("hoodie");

// 2. Promote the prop to a figure. Consumes the prop node in place (it stops being separately
//    findable by its old label) and returns a new DzFigure with ONE placeholder root bone.
var newFig = new DzFigure();
var converted = newFig.convertPropToFigure(propNode, "hoodie_root", /*localMaps*/ false, /*inheritSkeleton*/ false);
// converted.getLabel() === "Figure: hoodie" (Daz's own naming convention, not something you set)

// 3. Transfer real bone weights from the posable source figure onto it.
var xfer = new DzTransferUtility();
xfer.setSource(sourceFigureNode);      // the rigged, posable body figure
xfer.setTarget(converted);
xfer.setTransferBinding(true);         // the actual weight computation
xfer.setTransferUVs(false);            // UVs are already correct from export
xfer.setTransferMorphs(false);         // handle morphs separately if needed
xfer.setFitToFigure(true);
xfer.setParentToFigure(true);
xfer.setMergeHierarchies(false);
var ok = xfer.doTransfer();            // returns boolean
```

Confirmed live: after `doTransfer()`, the target figure still has only its one placeholder bone
as a scene-graph child (`getNumNodeChildren() == 1`), but its `SkinBinding` modifier is now
present and posing the SOURCE figure's bones (e.g. `chest`, `head`) measurably deforms the
target — its world bounding box changes shape (not just rigid-body follows). The skin binding
evidently references the source figure's real bones directly, cross-figure — no local bone copy
needed. Validated across 5 simultaneous attachments (clothing, hair, eyes, etc.) on a real
95-bone production character.

`DzTransferUtility` has many more knobs worth knowing about for tuning quality:
`setAdaptiveTolerance()`, `setNearness()`/`setUseNearness()`, `setRespectHiddenFacets()`,
`setSmartLeftRightHandling()`, `setAddSmoothModifier()`, `setVertexFirstProjection()`,
`setUVSpaceProjection()` — not yet tuned/validated individually, defaults were sufficient for the
first working pass. `getMorphTransferList()`/`setTransferSourceMorphs()` exist if morphs need to
ride along with the same transfer instead of being handled separately.

**Gotcha: OBJ import is not scriptable-silent.** Importing a `.obj` always triggers an interactive
"OBJ Import Options" dialog (scale/axis conversion) with no headless equivalent — confirmed live,
defaulted to a nonsensical 24384% scale, and a MODAL dialog cannot be dismissed via `daz_execute`
(it blocks the whole app). Build/load prop geometry as a plain `.duf` node instead (vertices
already in Daz cm/Y-up space) — loads exactly like any other file this pipeline produces, no
dialog, guaranteed-correct scale.

## Joint Controlled Morphs (JCMs) — correcting pinch/stretch at extreme poses

A JCM is a corrective shape (sculpted at a specific problem pose, e.g. shoulder bent 90°) that
smoothly dials in as a bone's rotation approaches that angle, and dials back out toward rest.
Reference: https://www.versluis.com/2021/08/jcms/ (manual GUI workflow),
Daz docs "Creating Morph Controlled Morphs" (the morph-driven variant, MCM, using the same ERC
machinery but controlled by another morph's value instead of a bone angle).

**Fully scriptable via the ERC (Evaluate Related Channels) system:**

```javascript
// Manual-GUI-equivalent: pose the joint to the target angle, dial the morph to 1.0, THEN freeze.
var freeze = new DzERCFreeze();
freeze.setControllerNode(shoulderBone);           // the DzNode the driving property lives on
freeze.setControllerProperty(shoulderBone.findProperty("YRotate"));  // the driving DzNumericProperty
freeze.setKeyed(true);                             // smooth keyed curve, not a flat linear ramp
freeze.addPropertiesToFreeze(targetNode);          // auto-detects properties currently off-default
// or: freeze.setPropertiesToFreeze([morphValueProp]);  // explicit control instead
var success = freeze.doFreeze();
```

`DzERCFreeze` captures the CURRENT state at freeze time as the curve's peak — the joint must
already be posed to the target angle and the morph dialed to its corrective value before calling
`doFreeze()`. This is the literal script equivalent of the manual "drag onto controller, then
ERC Freeze" workflow.

**Lower-level alternative — build the link by hand, no posing required:**

```javascript
var link = someMorphValueProp.getErcController ? null : null; // (see DzSceneHelper below)
// DzERCLink formulas (6 types): DeltaAdd f(v)=v+(c*m)+a, Multiply f(v)=c*v+a, Divide{Into,By},
// Subtract, Add, and Keyed f(v)=v+P(c) - a spline evaluated at the controller's current value.
// For Keyed, add explicit control points (Kochanek-Bartels tension/continuity/bias):
link.addKeyValue(/*key=controller value*/ 0, /*value*/ 0.0);
link.addKeyValue(/*key*/ 90, /*value*/ 1.0, /*t*/ 0, /*c*/ 0, /*b*/ 0);
```

**`DzSceneHelper`** (a general-purpose utility class, useful for both of the above) exposes:
- `createLink(bone, propertyName, controlBone, controllerName, type, scalar, addend): DzERCLink` —
  one-call simple (non-keyed) link between two named properties on two nodes.
- `createMorph(bone, name, deltas, overwrite): DzMorph` — creates a morph **directly from raw
  per-vertex delta data**, no Morph Loader Pro / OBJ-diff round-trip needed. If delta data is
  already computed on the exporting side (e.g. from Blender shape keys, already the case for this
  project's regular morph export), this is the direct path to get it into Daz as a `DzMorph`
  without ever writing an intermediate OBJ.
- `getErcController(controlledProp, controllingProp): DzERCLink` — read back an existing link.
- `findPropertyOnNode`/`findPropertyByLabel`/etc. — property lookup helpers, useful for finding
  the exact rotation-channel property object needed above (`YRotate`/`XRotate`/`ZRotate` are the
  internal names — see SKILL_DAZSCRIPT.md's "Common Property Internal Names").

**Not yet live-validated** (found via `daz_script_spec.d.ts` + the two reference articles above,
not yet exercised against a real corrective-morph pose in this project) — treat the exact call
sequence above as a strong starting point, not confirmed-working DazScript. Validate with a single
worst-offender corrective (e.g. one shoulder/collar pinch) before generalizing to a batch pipeline.

## Other gotchas found during this investigation (general DazScript reliability, not rigging-specific)

- **A live `daz_execute` property edit can silently fail to affect the next `daz_render_async`
  call**, with the edit still reading back correctly via `daz_get_material`/`findProperty` — no
  error anywhere. Root cause not pinned down (suspect: Iray's converted-scene cache not being
  invalidated by a scripted property write the way a UI-driven edit would invalidate it).
  **Workaround: render DURATION is a reliable tell.** A genuinely-applied structural change (e.g.
  hiding a whole node, zeroing a whole material's opacity) measurably changes render time (observed:
  ~8s → ~1.6–2.4s when a large chunk of geometry was actually removed from the render). A
  same-duration render after a property edit is a strong signal the edit never reached Iray —
  don't trust a visually-identical-looking render as proof an edit had no effect; check duration
  too, or force a genuinely large/structural change to confirm the pipeline is even responsive.
- **`prop.setMap(path)` to a nonexistent file can hang the entire DazScriptServer indefinitely.**
  Confirmed live: Daz Studio froze completely, showing a "Missing File (Not Responding)" dialog
  that never resolves on its own — required a manual Task-Manager-level process kill/restart, no
  script-side recovery possible once triggered. Always verify a texture file exists on disk
  (`os.path.isfile()` on the Blender/export side) before ever calling `setMap()` with it in a live
  script.
